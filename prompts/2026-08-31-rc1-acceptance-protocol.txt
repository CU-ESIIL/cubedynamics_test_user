==================================================
PHASE A — GENUINELY NAIVE USER
==================================================

This phase is the most important part of the experiment.

Start a fresh agent/session that has NOT read:

- CubeDynamics source
- CubeDynamics tests
- the systematic acceptance matrix
- expected API names
- known package capabilities
- known failure modes
- maintainer notes about how CubeDynamics is supposed to work

Give that agent only this goal:

"You are an environmental scientist who has discovered CubeDynamics. Figure out what it does, install the public release, and try to use it to perform useful environmental data analysis. Behave as you normally would when evaluating an unfamiliar scientific Python package. Record what you try, what you expect to happen, what actually happens, what confuses you, and what you learn."

Do not give the agent a tutorial.

Do not tell it which documentation page to read first.

Do not give it example commands beyond what an ordinary user can discover from public-facing materials.

Do not tell it the nouns, verbs, sources, or intended grammar in advance.

Let discoverability itself be part of the test.

The naive user should attempt to answer practical questions such as:

- What is CubeDynamics?
- Why would I use it?
- Can I install it?
- What is the first useful thing I can do?
- How do I discover available environmental data?
- How do I discover available analytical operations?
- Can I understand the grammar without maintainer assistance?
- Can I retrieve real environmental data?
- Can I transform it?
- Can I combine observations?
- Can I inspect what I have done?
- Can I get back an ordinary scientific Python object?
- When I make a mistake, does CubeDynamics help me recover?

But DO NOT turn this list into instructions for how to accomplish those tasks.

Allow the naive agent to explore naturally.

Capture the complete chronological session.

At minimum preserve:

artifacts/naive_session.jsonl
reports/naive_session.md

The report must distinguish:

- what the user discovered independently
- what documentation led them to
- successful actions
- failed actions
- confusion
- wrong assumptions
- recovery paths
- points where they would plausibly give up
- things that felt surprisingly easy
- things that required specialist knowledge

Once Phase A is complete, FREEZE its evidence.

Do not revise or clean it after learning more about CubeDynamics.

==================================================
PHASE B — SYSTEMATIC PUBLIC-SURFACE ACCEPTANCE
==================================================

Only after Phase A is frozen, begin systematic testing.

Use ONLY public user-facing CubeDynamics surfaces.

Construct an inventory of the public grammar as a user can discover it.

Test every publicly documented:

- noun
- source flavor
- verb
- modifier/parameter family
- inspection mechanism
- unwrap/export mechanism
- extension mechanism

For each feature determine:

1. Is it discoverable?
2. Is its purpose understandable?
3. Can a user construct it correctly?
4. Does it operate on an appropriate object?
5. Does semantic state change as expected?
6. Does the trace preserve what happened?
7. Does the result remain interoperable with ordinary scientific Python?
8. Are invalid uses rejected clearly?
9. Can the user recover from the error without reading source code?

Build a machine-readable coverage matrix.

Do not merely test that functions execute.

Test whether the package communicates scientific meaning.

==================================================
COMPOSITION AND ORDER
==================================================

CubeDynamics claims that authored analytical order carries scientific meaning.

Test this explicitly.

Construct analyses in which:

- changing operation order changes the scientific question
- operations remove dimensions
- operations create conditions
- temporal variation is retained or removed
- an operation becomes invalid after an earlier transformation
- two observations are combined
- source identity remains distinguishable
- unwrap and re-entry into ordinary scientific Python remain possible

Where two orders are both mathematically valid, determine whether their meanings remain understandable.

Where an order should be semantically invalid, determine whether CubeDynamics rejects it with a useful explanation.

Do not assume expected behavior merely because documentation claims it.

Observe and record actual behavior.

==================================================
REAL ENVIRONMENTAL SCIENCE
==================================================

The package should be tested as a scientific tool, not merely as an API.

Create at least 10 ORIGINAL environmental science questions that are NOT copied from CubeDynamics documentation.

They should vary across:

- climate
- weather
- vegetation
- disturbance
- hydrology or water availability where supported
- remote sensing where supported
- spatial analysis
- temporal analysis
- thresholds
- anomalies
- reductions
- events
- multi-variable composition

Questions should sound like questions a working environmental scientist might actually ask.

For each question:

1. Write the scientific question in plain language.
2. Predict how you think CubeDynamics might express it.
3. Attempt the analysis using only public interfaces.
4. Record the final expression.
5. Inspect its semantic state and trace.
6. Examine the resulting scientific object.
7. Determine whether the expression still communicates the original scientific question.
8. Record any scientific assumptions CubeDynamics makes visible.
9. Record important assumptions CubeDynamics does NOT make visible.
10. Give the individual analysis a PASS, PASS WITH CAVEATS, or FAIL.

Favor real public data when practical.

Do not silently substitute toy data when a documented public data path is supposed to work.

If live data fail, distinguish:

- CubeDynamics failure
- provider failure
- network failure
- authentication problem
- data availability problem
- unclear documentation

==================================================

- trace
- result type/dimensions
- warning/error

Store machine-readable results.

==================================================
NOVICE MISTAKES
==================================================

Deliberately make realistic mistakes.

Examples include:

- wrong parameter names
- missing required parameters
- wrong dimensions
- operations in an inappropriate order
- incompatible observations
- incompatible spatial or temporal structures
- assumptions that similarly named data products are interchangeable
- attempting event detection after temporal variation has disappeared
- attempting reductions on unavailable dimensions
- misunderstanding source-specific behavior

Judge errors from the perspective of a scientist who does NOT know the implementation.

A good error should help the scientist understand:

- what is wrong
- why it is wrong
- what scientific object they currently have
- what kinds of next actions are valid

==================================================
ACCEPTANCE STANDARD
==================================================

The question is NOT:

"Does CubeDynamics have bugs?"

The question is:

"Can a competent environmental scientist who did not develop CubeDynamics discover it, install it, understand its analytical grammar, perform meaningful environmental analyses, understand what the package did, recover from reasonable mistakes, and trust the evidence well enough to continue using it?"

At the end give exactly one primary verdict:

READY FOR HUMAN OUTSIDE TEST

or

FIX BEFORE HUMAN OUTSIDE TEST

Then explain the verdict.

A package does not need to be perfect to receive READY FOR HUMAN OUTSIDE TEST.

Use FIX BEFORE HUMAN OUTSIDE TEST only when failures are likely to prevent or seriously mislead a real outside scientist.
