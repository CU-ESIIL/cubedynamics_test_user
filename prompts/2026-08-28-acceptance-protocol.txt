==================================================
PURPOSE OF THIS RUN
==================================================

We believe CubeDynamics is approaching its first public release.

Internal tests answer questions such as:

    Does the implementation behave as expected?
    Do known workflows pass?
    Do release artifacts install?
    Do documented examples execute?

This repository must answer a different question:

    What actually happens when a competent scientist who has never
    developed CubeDynamics tries to use it?

We want to discover problems BEFORE a human outside-user test.

This should be a genuine black-box acceptance experiment.

The tester should be scientifically competent and comfortable with Python and
environmental data, but should have no privileged knowledge of CubeDynamics.

==================================================
1. VERIFY THE TEST BOUNDARY
==================================================

Before doing anything else, inspect this repository's AGENTS.md and existing
documentation.

Confirm that the naive-user boundary is explicit.

During the naive-user phase, the tester must NOT:

- clone CU-ESIIL/cubedynamics
- inspect its source code
- inspect its tests
- inspect its AGENTS.md
- inspect its PROMPT_LOG.md
- inspect developer documentation not presented to ordinary users
- use CubeDynamics repository-local fixtures
- mount a CubeDynamics checkout
- search CubeDynamics source to understand an error
- patch the installed CubeDynamics package
- use implementation details to discover undocumented behavior

The tester MAY use:

- this cubedynamics_test_user repository
- an installed CubeDynamics release artifact
- the public CubeDynamics website
- the public CubeDynamics README and normal repository landing information
- normal Python help/introspection available to an installed-package user
- public environmental data services
- ordinary scientific Python tools

If the current AGENTS.md already establishes this correctly, preserve it.

Do not weaken this boundary.

==================================================
3. SEPARATE THE TEST INTO TWO MODES
==================================================

This is important.

Do NOT begin with an exhaustive scripted checklist.

Run two distinct phases:

    A. NAIVE EXPLORATORY USER
    B. SYSTEMATIC PUBLIC-SURFACE COVERAGE

The first tells us whether CubeDynamics is understandable.

The second tells us whether CubeDynamics is complete and robust.

Do not allow knowledge gained from CubeDynamics internals in either phase.

==================================================
PHASE A — NAIVE EXPLORATORY USER
==================================================

Start with a fresh agent context if possible.

Give the tester only this goal:

    "You are an environmental scientist who has discovered CubeDynamics.
    Figure out what it does and try to use it for environmental analysis.
    Explore what you can do with it. Use its public documentation when
    you need help. Try increasingly ambitious analyses. Keep going when
    reasonable, and record everything that happens."

Do NOT initially give this agent:

- a list of CubeDynamics nouns
- a list of CubeDynamics verbs
- internal architecture
- known-good examples beyond what it discovers publicly
- known limitations
- expected answers
- our previous CubeDynamics development history

We specifically want to observe DISCOVERY.

Record chronologically:

- where the user starts
- what documentation they choose
- what they think CubeDynamics is
- what they try first
- what they expect to happen
- what actually happens
- where they become confused
- what terminology they infer correctly
- what terminology they misunderstand
- what documentation they search for
- how they recover from errors
- where they get stuck
- what capabilities they discover naturally
- what capabilities they never discover
- what they attempt that CubeDynamics does not support

This phase should feel like a real user session rather than a test suite.

Let the tester formulate its own scientific questions.

Encourage increasing complexity:

simple analysis
→ transformation
→ composition
→ multiple transformations
→ visualization
→ comparison
→ more original scientific questions
→ extension/customization

Do not stop at the first successful example.

Spend substantial time exploring.

Preserve the complete chronological session as evidence.

==================================================
6. TEST EVERY DOCUMENTED NOUN AND SOURCE
==================================================

For every documented production-supported noun:

figure out how to use it from the public documentation.

Use the smallest practical request.

Attempt to:

- obtain/create it
- inspect dimensions
- inspect coordinates
- inspect units
- inspect attributes
- inspect source identity
- inspect provenance
- visualize it where appropriate
- perform meaningful transformations

For every documented source flavor:

attempt it independently.

If multiple sources provide the same noun, compare them as a naive scientist
might.

Do NOT assume scientifically different sources should produce identical
results.

Evaluate whether CubeDynamics makes their identity and differences visible.

Candidate, experimental, blocked, deprecated, or unavailable sources must
remain visibly distinguishable from production-supported sources.

Never fabricate a successful live retrieval.

==================================================
7. TEST EVERY DOCUMENTED PUBLIC VERB
==================================================

For every public verb discovered through user-facing material:

1. infer its purpose from documentation
2. find a reasonable valid input
3. execute it
4. inspect the result
5. evaluate dimensions
6. evaluate coordinates
7. evaluate attributes
8. evaluate provenance where relevant
9. visualize the result where meaningful
10. try a reasonable edge case

Every documented verb should receive at least one valid execution attempt.

Where appropriate, also misuse it in a way a normal new user plausibly would.

Evaluate the error experience.

Flag cases where:

- documentation is insufficient
- arguments are unclear
- defaults are surprising
- dimensions disappear unexpectedly
- metadata disappears unexpectedly
- provenance becomes unclear
- operation order becomes scientifically ambiguous
- an error is cryptic
- invalid behavior silently succeeds

==================================================
8. TEST COMPOSITION AGGRESSIVELY
==================================================

CubeDynamics is a compositional grammar, so individual function success is
not sufficient.

Exercise many meaningful pipelines.

Include:

noun
| verb

noun
| verb
| verb

noun
| verb
| verb
| verb

and longer pipelines.

For verb pairs where order could reasonably matter, try both:

A | verb1 | verb2

and

A | verb2 | verb1

Do NOT expect them to be equal.

Instead evaluate whether:

- both execute when scientifically valid
- differences are understandable
- dimensions remain coherent
- metadata remains coherent
- provenance records the sequence
- the user can understand what the operation order means

Programmatically generate additional plausible combinations.

Do not waste the test on obviously meaningless combinations.

However, include combinations that a reasonable novice might THINK are valid.

Those failures are useful.
